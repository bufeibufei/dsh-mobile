# B0 发送图片改进提案 v1

只改"怎么把图片放进输入框"，不改 DSH 本体、服务端和模型。范围包括：Android 壳的选择器、图片预处理，以及 `mobile-ui` 的一个快捷按钮。定位另行设计。

## 1. 现状

调用链：输入框 "+"（`添加文件或调用指令`）→ 菜单项 "文件" → 官方隐藏的 `<input type="file" multiple>` → WebView `onShowFileChooser` → 壳里的 `params.createIntent()`（`B0Activity.kt`）。

问题：

1. **打开的是系统"文件"选择器**：`createIntent()` 是通用的文档选择，不是相册。找照片要进目录层层翻，没有按时间排列的缩略图墙。
2. **不能拍照**：要先退出 App 去相机拍，再回来从文件里找。
3. **入口深**：选一张图至少要点 "+"、"文件"、进相册目录、选图，共四步以上，还不算翻找。
4. **原图直传**：手机照片一般 3～12 MB，移动网络下上传慢。服务端（`dsh-attachment-local`）收到后会把总像素压到 2048×2048（约 419 万）以内、≤4 MB，并去掉元数据，所以多传的字节到了服务端就被丢掉。
5. **HEIC 照片模型看不到**：服务端和官方输入框只把 `image/png|jpeg|webp|gif` 当图片。很多手机相机默认存 HEIC，这类照片会走普通文件路径，模型看不到画面，生活记录也不会挂上这张图。

不需要改的部分：线上 `deepseek-flash` 支持看图；服务端单张上限 20 MB、每条最多 20 张；生活记录会把当条消息的图片挂到记录上。

## 2. 目标体验

- 输入框左侧新增**图片按钮**，点一下弹出"拍照 / 从相册选择 / 选择文件"。从相册选一张图共 3 步：点按钮、点"从相册选择"、点照片并确认。
- 原来 "+ → 文件" 的入口保留，也弹出同一个面板。
- 拍照：调用系统相机，拍完直接回到输入框，附件栏出现这张图。
- 相册：系统照片选择器，按时间排列，可以多选。
- 文件：和现在一样，使用系统文件选择器，不做任何处理（用于 PDF 等非图片）。
- 从相册或相机进来的图片都在手机上先处理：转成 JPEG、缩小、去掉元数据，然后交给网页。用户看到的附件就是处理后的图。

## 3. 壳：选择面板（`android/b0`）

`onShowFileChooser` 不再直接启动 `params.createIntent()`，改为：

1. 读 `params.acceptTypes` 和 `params.mode`：
   - 页面只接受非图片类型时，直接走"文件"；
   - `MODE_OPEN`（单选）时，相册只允许选一张。
2. 弹出原生底部面板（与现有的提示、外链确认同一套样式），有"拍照""从相册选择""选择文件""取消"四项。
   - 手机上找不到相机应用时，隐藏"拍照"。为此要在 Manifest 里加 `<queries>` 声明 `IMAGE_CAPTURE`，否则 Android 11 以上查不到。
   - 点"取消"、点面板外或按返回键，都回调 `null`，与现在取消系统选择器的效果相同。返回键先关面板，不交给网页。
3. 各项的实现：
   - **相册**：如果系统照片选择器可用（`ActivityResultContracts.PickVisualMedia.isPhotoPickerAvailable`），用 `PickMultipleVisualMedia(9)`，只选图片。不可用时，改用 `ACTION_GET_CONTENT` 加 `image/*` 和 `EXTRA_ALLOW_MULTIPLE`。很多国产系统没有照片选择器，这个 Intent 一般会列出系统图库。两条路都不需要存储权限。
   - **拍照**：`ACTION_IMAGE_CAPTURE`，`EXTRA_OUTPUT` 指向本应用 FileProvider 下的临时文件。Manifest 不声明 `CAMERA` 权限，因为调用系统相机不需要这个权限；而一旦声明了，系统反而会要求先获得授权。
   - **文件**：保持 `params.createIntent()` 原样。
4. 现有的 `fileResult` 单一回调、页面变化或切 Host 时作废等规则保持不变。新的结果处理同样先核对当前 WebView 和 Host，再回调；对不上就回调 `null`。

已知限制：如果系统在相机运行时回收了 App 进程，回来后 WebView 已经重建，原来的回调不存在了，这次选择会丢失，需要重新选。不做跨进程恢复。

## 4. 壳：图片预处理

只处理来自"相册"和"拍照"的图片；"文件"入口返回的内容一律不处理。

| 输入 | 处理 |
| --- | --- |
| JPEG / HEIC / HEIF / WebP / PNG（无透明） | 解码，按 EXIF 方向转正，等比缩小到总像素 ≤ 2048×2048，编码为 JPEG，质量 85 |
| PNG（有透明像素） | 同样缩小，编码为 PNG |
| GIF | 原样交出，保留动图，大小由服务端的现有上限检查 |
| 解码失败 | 跳过这一张，提示"有 N 张图片无法读取，已跳过" |

- 像素上限与服务端的规范化上限（`normalizedImageMaxPixels` 默认 2048×2048）一致，按总像素而不是长边限制，长截图不会被压窄。处理后的图不带元数据，并且在服务端的限制以内，服务端会原样保存，不再压第二次，模型看到的清晰度和现在一样。1200 万像素的照片处理后约 2365×1774，质量 85 时一般在 0.5～1.5 MB。
- 重新编码只写像素，不带元数据。这和服务端现在的做法相同（服务端本来就会去掉元数据），所以隐私上没有变化，只是不再上传这些字节。
- 解码时先读尺寸，再按目标尺寸采样解码：API 28 及以上用 `ImageDecoder.setTargetSize`，以下用 `BitmapFactory` 的 `inSampleSize`。这样 5000 万像素的照片也不会把整张原图读进内存。HEIC 的解码依赖系统自带的解码器（Android 9 起才有），解不了的按上表跳过。解码时统一转成 8 位 sRGB（新手机拍的照片常是 Display P3），否则服务端会判定不能原样保存而再编码一次。
- 在后台线程处理。超过 300 ms 时在页面上显示"正在处理图片…"，处理完后一次性回调给网页。
- 输出文件放在 `cacheDir/b0-images/`，通过 FileProvider（authority 为 `com.jarvis.life.b0.images`）生成 `content://` URI 交给 WebView。文件名为 `IMG_<yyyyMMdd_HHmmss>_<序号>.jpg`，时间取处理时刻，不读 EXIF。
- WebView 会在发送时才读取文件，所以不能立即删除临时文件。App 启动时和每次打开面板时，删除 24 小时之前生成的文件。

## 5. `mobile-ui`：图片快捷按钮

- 在官方插件位 `conversation.input.left` 放一个图片图标按钮，使用官方图标库，尺寸与输入框里其它按钮一致。
- 点击时调用官方"文件"动作背后的同一个入口（`commandUi` 注册的 `file` 动作，内部是 `inputHub.pickFiles(sessionId)`），然后由壳弹出第 3 节的面板。按钮不经过新的原生桥，不新增任何消息。
- 只在官方判定可以添加文件时（`canPickFiles` 为真）可点，其它时候显示为禁用。
- 只在移动布局（宽度 ≤ 700 CSS px）显示，桌面布局保持官方原样。
- 用旧 APK 时，按钮照样能用，只是打开的仍是旧的文件选择器。因此 `mobile-ui` 可以先于 APK 单独上线。

## 7. 测试与验收

自动测试（行为测试，不切源码）：

- Kotlin 单元测试覆盖纯逻辑：目标尺寸计算（横竖图、长截图、小图不放大、正好 2048×2048）、EXIF 方向到旋转角度的映射、按 `acceptTypes` 和 `mode` 决定面板项、输入格式到输出格式的映射、临时文件的过期判断。
- `mobile-ui` DOM 测试：移动宽度下按钮出现、桌面宽度下不出现、点击调用 `pickFiles`、`canPickFiles` 为假时禁用。
- 构建：`./gradlew --offline :b0:testDebugUnitTest :b0:assembleDebug`；`mobile-ui` 的现有冒烟检查。

需要在实体手机上由用户验收（编译通过不等于真机可用）：

1. 用相机拍一张，回到输入框后能看到这张图，发送后模型能描述画面。
2. 从相册多选 3 张，其中至少 1 张 HEIC，3 张都以图片附件发出。
3. 一张 10 MB 以上的原图，处理后附件在 1.5 MB 以内，上传明显比现在快。
4. 选"文件"发送一个 PDF，行为与现在一致。
5. 在面板上按返回键或点"取消"，什么都不添加，输入框照常可用。
6. 拍照过程中切到别的应用再回来，不崩溃。

## 8. 不在本次范围

定位、视频、裁剪和编辑、读取照片拍摄时间并告诉模型、服务端支持 HEIC。

## 9. 待确认

2. 相册一次最多选 9 张（服务端上限是 20）。**建议 9 张。**
3. 快捷按钮只在移动布局显示。**建议如此。**
4. 无法解码的图片跳过并提示，而不是当作普通文件发出（发出去模型也看不到）。**建议跳过。**
